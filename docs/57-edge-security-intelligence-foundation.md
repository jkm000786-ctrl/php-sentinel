# Edge Security Intelligence Foundation

PHP Sentinel must distinguish application evidence from responses generated by
CDNs, reverse proxies, WAFs, rate limiters, and bot-management systems.

## Security objective

An edge response must never increase confidence in a PHP runtime or CVE
conclusion merely because the response is reachable over HTTP.

The edge subsystem is evidence-driven and passive. It does not perform WAF
bypass, CAPTCHA solving, anti-bot circumvention, origin discovery, or evasive
request mutation against public targets.

## Initial response classes

- `application_response`
- `edge_response`
- `waf_block`
- `bot_challenge`
- `rate_limit`
- `origin_failure`
- `unknown`

## Application reachability

Reachability is modeled independently from provider identification:

- `confirmed`
- `probable`
- `unknown`
- `not_reached`

Phase 57 intentionally does not claim `confirmed` reachability from passive
edge fingerprinting alone. Later pipeline integration may promote reachability
only when independent application-specific evidence justifies it.

## Provider evidence

The initial detector supports conservative fingerprints for:

- Cloudflare
- Akamai
- Imperva / Incapsula
- Fastly
- BunnyCDN
- ModSecurity
- generic CDN/WAF evidence

Provider confidence is derived from multiple observable signals. A generic HTTP
403 is not classified as a WAF block without WAF-specific evidence.

## Fail-closed semantics

Bot challenges, explicit WAF blocks, and recognized edge origin failures are
classified as `not_reached`. HTTP 429 is classified as a rate-limit response
with unknown application reachability.

This subsystem is an observation layer only. Phase 59 will bind edge decisions
into unified assessment, cross-layer consistency, findings, and provenance.
